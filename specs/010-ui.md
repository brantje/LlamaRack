# 010 — Web UI

Status: Draft

Related issue: #1

## 1. Purpose

The UI must clearly separate **Models** from **Instances**:

- **Models** are registered model inventory plus reusable llama.cpp defaults.
- **Instances** are durable `llama-server` process definitions and the operational control plane.

Runtime state and lifecycle controls belong to Instances, not Models.

## 2. Primary navigation

- Dashboard
- Models
- Instances
- Discover
- Downloads
- API
- Settings

`Instances` is a first-class top-level route.

## 3. `/models`

`/models` lists only Models registered in the database.

Use a table with:

- Name
- Path
- Size
- Quantization
- Context capability
- Actions

Actions:

- Edit
- Delete

Do not show:

- READY/UNLOADED/FAILED state;
- Always On;
- Autoload;
- resource-pressure eviction;
- priority;
- GPU placement;
- VRAM/runtime metrics;
- active requests;
- Start/Stop/Restart/Kill.

`/models` is inventory/configuration only.

## 4. Model create/edit

Keep:

```text
/models/new
/models/:id/edit
```

These manage:

- Model name/identity;
- artifact association;
- reusable Model-level llama.cpp Basic/Advanced overrides.

A Model may exist with zero Instances.

## 5. Optional first Instance on `/models/new`

Model creation may optionally bootstrap a first Instance.

Keep this section intentionally small.

Allowed fields:

- Instance name;
- derived Instance ID preview;
- Always On;
- Autoload on request;
- Allow resource-pressure eviction;
- Start after creation.

Do **not** expose here:

- GPU selection;
- tensor split;
- priority;
- Instance llama.cpp overrides;
- idle/startup timeout;
- advanced scheduler settings.

Full Instance configuration belongs on `/instances/new` and `/instances/:id/edit`.

## 6. Instance name → ID behavior

Instance identity behaves like slug-based model creation:

```text
Instance name
   -> slugify
   -> instance.id
   -> OpenAI `model` value
```

Example:

```text
Name: Qwen Coding 32B
ID:   qwen-coding-32b
```

The UI should show the derived ID while the user types.

There is no separate public alias/model-ID field.

Slug collisions must be validated before save.

## 7. Instance rename

Renaming an Instance changes its slug-derived `instance.id` and therefore changes the OpenAI `model` value clients use.

Before saving a rename, show an explicit API-breaking warning, for example:

> Renaming this Instance changes its API model ID from `qwen-coding` to `qwen-coding-v2`. Existing clients using the old ID will stop working.

Require confirmation.

No old-ID compatibility alias is retained in v1.

## 8. `/instances`

`/instances` is the `llama-server` control plane and keeps the current card-oriented layout.

Stopped Instances remain visible.

Each card should show as available:

- Instance name;
- `instance.id` / API model ID;
- referenced Model;
- lifecycle state;
- Always On;
- Autoload on request;
- eviction policy;
- placement summary;
- later runtime metrics/health/log indicators.

## 9. Instance actions

Support:

- Launch
- Stop
- Restart
- Kill
- Duplicate
- Edit/Reconfigure
- View logs
- Delete

Actions depend on state.

`Kill` is explicitly different from graceful Stop and should warn that active requests may be terminated immediately.

## 10. `/instances/new`

Full Instance creation flow:

1. select registered Model;
2. enter Instance name;
3. preview slug-derived `instance.id`;
4. configure lifecycle policy;
5. configure resource/scheduler policy;
6. configure Instance llama.cpp overrides;
7. configure GPU placement/tensor split;
8. validate;
9. save;
10. optionally launch.

## 11. Instance configuration

### Lifecycle

- Always On
- Autoload on request
- idle timeout where exposed
- startup timeout where exposed

### Resource policy

- priority
- Allow resource-pressure eviction

### llama.cpp

- inherited Model values;
- per-Instance Basic overrides;
- per-Instance Advanced overrides;
- visible inheritance/source indicators.

### Placement

- Automatic placement
- Manual GPU selection
- Automatic tensor split
- Manual tensor split

## 12. Configuration inheritance

Show effective value source:

```text
Upstream default
Global default
Model override
Instance override
```

Removing an Instance override restores Model/Global inheritance.

Do not copy inherited values into the Instance merely to display them.

## 13. Running Instance edits

If a running Instance receives a runtime-affecting edit, show confirmation:

> Saving these changes will restart this Instance. It may be temporarily unavailable and active work may be interrupted.

Actions:

```text
Cancel
Save & Restart
```

On confirmation:

```text
persist
-> drain
-> stop
-> launch
-> READY/FAILED
```

Direct Instance edits do not use a normal long-lived “Save now, restart later” flow.

Rename also requires the separate API-ID-change warning.

## 14. Model/global config changes

Model/global llama.cpp changes may affect multiple running Instances through inheritance.

These broader changes may show impact and mark affected Instances restart-required rather than automatically restarting every worker.

## 15. Lifecycle UX

### Launch

Show `QUEUED`/`STARTING` immediately after accepted request.

### Loading

Show `LOADING` distinctly.

### Stop

Gracefully drain and stop.

If the Instance is Always On, manual Stop is still allowed. The manager temporarily suppresses Always-On reconciliation for the current manager session so it remains stopped.

Suppression ends on:

- manual Launch;
- inference request targeting that Instance;
- manager restart.

### Restart

Warn about temporary unavailability and perform controlled restart.

### Failed

Show failure classification, retry, edit and logs.

## 16. Manual launch eviction warning

When a manual Launch may need resource-pressure eviction, show confirmation:

> Starting this Instance may stop other idle Instances automatically to free RAM/VRAM according to the configured resource policy.

Actions:

```text
Cancel
Launch
```

The user does not choose victims. Scheduler policy selects them automatically.

Inference-triggered autoload does not wait for an interactive confirmation.

## 17. Always On vs eviction protection

Make the distinction explicit:

- **Always On** — proactively keep this exact Instance running except during temporary manual-stop suppression.
- **Allow resource-pressure eviction** — whether this loaded Instance may be stopped to make room for another Instance.

Supported combination:

```text
Always On: Off
Autoload on request: On
Allow resource-pressure eviction: Off
```

Meaning: load on demand, then protect it from normal resource-pressure eviction.

## 18. GPU placement UX

Phase 7 Instance placement editor supports:

- Automatic placement;
- Manual GPU selection;
- Automatic tensor split;
- Manual tensor split.

Show free/total VRAM, estimated demand, fit warnings and missing configured GPUs.

Automatic placement is **single-GPU first**. One fitting GPU should be selected rather than letting llama.cpp spread across every visible GPU.

## 19. Observability

As later phases implement telemetry, `/instances` is the canonical home for:

- lifecycle state;
- PID/private port;
- uptime;
- health;
- GPU allocation;
- RAM/VRAM;
- active/queued requests;
- request count;
- last activity;
- load duration;
- errors;
- logs.

Do not add these operational fields back to `/models`.

## 20. Logs

Logs are Instance-specific and should support recent stdout/stderr, polling/refresh, pause, search/filter and raw access where supported.

## 21. API page

The API page must explain:

```text
Registered Model != OpenAI model ID
OpenAI model ID = instance.id
```

Example:

```text
Instance name: Qwen Coding 32B
Model ID:      qwen-coding-32b
```

OpenAI/LiteLLM examples use `instance.id`.

`/v1/models` lists addressable Instances; `/api/v1/models` lists registered Models.

## 22. Discover / Downloads

Completed downloads can open `/models/new`.

From there the user may optionally bootstrap the compact first Instance with only name + Always On + Autoload + eviction + start-after-create.

## 23. Development schema note

Phase 5.5 is development-time restructuring.

Do not require or add database migration files for this UI/domain change. The current development schema may be changed directly and development data recreated.

## 24. Accessibility / responsive behavior

- keyboard-accessible forms/dialogs;
- visible focus;
- accessible labels;
- state/error meaning not color-only;
- responsive Models table and Instance cards;
- long Instance IDs/options wrap/copy cleanly;
- destructive confirmations remain usable on small screens.

## 25. Acceptance criteria

- `/models` is a registered-Models-only table;
- Models table contains name/path/size/quantization/context capability + Edit/Delete;
- no lifecycle controls/runtime state appear on `/models`;
- `/models/new` retains Model llama.cpp configuration;
- `/models/new` optionally creates a first Instance with only name, Always On, Autoload, eviction and start choice;
- Instance name displays a slug/ID preview;
- `/instances` is top-level and card-based;
- stopped Instances remain visible;
- full Instance configuration lives on `/instances/new` and edit;
- `instance.id` is shown as the OpenAI model ID;
- renaming warns that the API model ID changes;
- direct running-Instance edits confirm and automatically restart;
- manual Stop of Always-On remains stopped for the current manager session;
- manual Launch warns about possible automatic eviction;
- Kill remains distinct from Stop;
- Duplicate requires/produces a new unique Instance name/slug;
- API examples use `instance.id` as `model`;
- runtime observability stays on Instances, not Models.
