# 010 — Web UI

Status: Draft

Related issue: #1

## 1. Purpose

This specification defines the Nuxt/Vue management interface for llamacpp-manager.

The UI is an operational console for model discovery, downloads, configuration, lifecycle, hardware placement, inference API access and system administration. It must make complex llama.cpp configuration approachable without hiding advanced capabilities.

## 2. UX principles

1. **Models first.** The main mental model is a configured public model, not a process or GGUF filename.
2. **Show desired and observed state separately.** A saved config can differ from what a running worker currently uses.
3. **Progressive complexity.** Common llama.cpp settings are easy to find; every discovered option remains available in Advanced mode.
4. **Explain resource decisions.** “Cannot start” must include why, not only a red status.
5. **Never make lifecycle actions ambiguous.** Starting, loading, draining, restart-required and failed states are visibly distinct.
6. **Operational density without clutter.** The product is a manager/dashboard, so tables and compact metrics are appropriate.
7. **Avoid destructive surprises.** Deleting a Model and deleting its multi-gigabyte artifact are separate actions.
8. **Responsive but desktop-first.** The primary environment is a desktop browser, while core status/actions remain usable on smaller screens.

## 3. Application shell

Primary navigation:

- Dashboard
- Models
- Discover
- Downloads
- API
- Settings

Global shell elements:

- application name/logo;
- current user menu;
- role indication where helpful;
- overall system/manager health indicator;
- active download indicator;
- optional compact aggregate GPU/resource indicator;
- logout.

Do not overload the top navigation with per-model operations.

## 4. Dashboard

The Dashboard is a combined operations view.

### 4.1 Summary cards

Show at minimum:

- configured models;
- loaded/READY models or instances;
- active requests;
- queued/load-waiting requests;
- aggregate generation throughput;
- error state/count summary;
- active downloads.

### 4.2 Hardware panel

Show:

- system RAM used/total;
- each NVIDIA/AMD GPU;
- VRAM used/total;
- utilization;
- currently assigned/running model instances where available.

Use clear numeric values plus compact bars. Do not rely on color alone to communicate fit/pressure.

### 4.3 Model activity

Show a compact table/list with:

- public model ID;
- state;
- ready instance count;
- active requests;
- tokens/sec or recent throughput;
- last used;
- Always-On badge;
- priority.

Clicking a row opens the model detail page.

### 4.4 Request/inference metrics

Show useful recent-window charts/cards for:

- requests/minute;
- latency;
- TTFT;
- input/output tokens per second;
- errors.

The exact chart library is implementation-specific. Avoid presenting empty charts when no data exists; show an informative empty state.

### 4.5 Downloads

If downloads are active, show compact progress and a link to Downloads.

### 4.6 Alerts/problems

Surface actionable conditions such as:

- Always-On model cannot be satisfied;
- worker failed repeatedly;
- configured GPU disappeared;
- llama.cpp option schema invalid/degraded;
- disk space low;
- Hugging Face authentication failure;
- restart required after config/global-default change.

Alerts link to the relevant remediation page.

## 5. Models list

Default view can be a data table with optional card mode later.

Columns:

- public model ID;
- display name optional;
- artifact/quantization;
- aggregate state;
- instances ready/defined;
- Always-On;
- priority;
- estimated/observed VRAM where useful;
- active requests;
- last used;
- restart-required indicator;
- row actions.

Controls:

- search by model ID/display/artifact;
- state filter;
- Always-On filter;
- priority filter;
- sort by name/state/last used/resource size;
- Create model;
- Start/Stop/Restart where authorized.

Read-only users do not see enabled mutation controls.

## 6. Create model workflow

Entry points:

- from a completed downloaded artifact;
- from Models -> Create, selecting an existing local artifact.

Flow:

1. choose artifact;
2. enter/suggest public model ID;
3. set basic lifecycle policy;
4. set basic llama.cpp configuration;
5. configure GPU placement/instance;
6. validate estimated fit;
7. save;
8. optionally start immediately.

Do not require starting the model to save it.

Public model ID implications should be clear because clients depend on it.

## 7. Model detail page

Tabs/sections:

- Overview
- Configuration
- Instances
- Metrics
- Logs
- Source

Persistent header should show:

- public model ID;
- current aggregate state;
- Always-On status;
- priority;
- current active requests;
- primary Start/Stop/Restart action appropriate to state;
- restart-required warning if applicable.

## 8. Model Overview

Show:

- lifecycle state and instance counts;
- artifact name/quantization/size;
- source provider/repository;
- Always-On;
- autoload;
- idle timeout;
- startup timeout;
- priority;
- routing policy;
- estimated RAM/VRAM;
- current observed allocation;
- last used;
- recent failure if present.

Provide concise explanation for FAILED/unschedulable states and link to logs/configuration.

## 9. Configuration — Basic

Basic mode contains curated commonly used llama.cpp settings generated from the option metadata system.

UX requirements:

- grouped sections such as Context, Performance, GPU, Sampling/Server, Cache, Templates/Reasoning, Specialized modes;
- friendly label;
- short explanation;
- current effective value;
- inherited/overridden indicator;
- reset-to-global action for overridden values;
- validation inline;
- mark options unavailable in current binary rather than showing controls that cannot work.

GPU placement belongs primarily to Instances/placement UI but model-level offload settings may be visible where relevant.

## 10. Configuration — Advanced

Advanced mode exposes every discovered configurable option.

Features:

- search by flag/description;
- category navigation/filter;
- show canonical CLI flag;
- show data type/control;
- source: upstream default / global / model override;
- explicit override toggle/edit;
- reset override;
- unsupported-retained warning;
- read-only display for manager-protected options;
- raw/unclassified input where schema inference is uncertain.

Advanced mode must remain usable with hundreds of options. Use virtualization/pagination/collapsible categories if needed.

## 11. Unsaved and restart-required configuration

Editing is local until Save.

Footer/action bar:

- Discard
- Save
- Save and restart (when model is running and user has permission)

After Save without restart:

- show `Restart required` if effective running configuration differs;
- explain that the current worker still uses its previous launch fingerprint;
- do not display changed values as “active” without qualification.

Global-default changes can mark multiple models restart-required.

## 12. Instances tab

List manually configured instance definitions.

For each instance:

- name/ID;
- enabled;
- runtime state;
- selected GPUs;
- tensor split summary;
- active requests;
- PID/private port only as secondary authorized diagnostics;
- load/start time;
- last failure;
- Start/Stop/Restart actions.

Allow creating another instance manually. Do not present automatic scaling controls in v1.

## 13. GPU assignment editor

The instance editor should visually list detected GPUs:

```text
[✓] GPU 0 — NVIDIA ...    12.1 / 24 GB VRAM
[✓] GPU 1 — NVIDIA ...     8.4 / 24 GB VRAM
```

Modes:

- Automatic placement
- Manual device selection

For multiple selected GPUs:

- Automatic tensor split
- Manual tensor split

Manual split UI should clearly communicate proportions/values and validate number of entries against selected GPUs.

Show:

- estimated allocation per device;
- current free/total VRAM;
- fit warning;
- scheduler safety margin;
- note that current free memory may change before startup.

If a configured GPU is missing, preserve the assignment and show a blocking warning instead of silently mapping another device.

## 14. Lifecycle action UX

### Start

When clicked:

- transition UI immediately to QUEUED/STARTING based on API response;
- show scheduling reason/progress where available;
- allow navigation away without losing state.

### Loading

Display model loading separately from generic spinner. Show elapsed load time and configured timeout where useful.

### Stop

For active requests, explain graceful draining if applicable.

For final Always-On instance, Stop should be disabled or invoke a dialog explaining that Always-On must be disabled first. Do not let it stop and instantly restart mysteriously.

### Restart

Warn that the model may be temporarily unavailable, especially with only one instance.

### Failed

Show:

- failure classification;
- concise message;
- retry/start action;
- link/open logs;
- configuration link for config-related failures.

## 15. Model Metrics tab

Per-model operational metrics:

- requests over time;
- active requests;
- load wait duration;
- average/p95 latency where available;
- TTFT;
- input/output tokens;
- generation throughput;
- errors;
- model load duration;
- instance comparison when multiple instances exist.

Do not imply long-term historical retention if the backend only retains recent in-memory/bounded data.

## 16. Logs tab

Allow selecting an instance and viewing captured stdout/stderr.

Features:

- recent lines;
- auto-refresh/poll toggle;
- pause scrolling;
- text search/filter in loaded window;
- severity/source where parsable;
- download/view raw log if backend exposes it;
- clear explanation when worker has never started.

Because management API is REST-only in v1, polling is acceptable. Avoid aggressive polling when tab is hidden.

Warn that upstream logs may contain request/model content depending on llama.cpp behavior.

## 17. Source tab

Show backing artifact/source information:

- local filename(s);
- total size;
- quantization;
- GGUF metadata summary;
- source provider;
- Hugging Face repository/revision or direct URL metadata (sanitized);
- split shard count;
- download timestamp;
- checksum if available.

Destructive artifact deletion should not live as a casual model action here unless user is Admin and references are clearly explained.

## 18. Discover page

The Discover page is a first-class Hugging Face browser.

Layout:

- search input;
- filters/sidebar or filter row;
- sorting;
- result list/cards;
- local hardware summary visible enough to interpret recommendations.

Result item may show:

- repository ID;
- author;
- relevant tags;
- downloads/likes where provided;
- last update;
- GGUF availability;
- best-fit/recommended candidate summary if already resolved;
- already downloaded indicator.

Search input should be debounced to avoid provider requests per keystroke.

## 19. Discover model detail

Show repository information plus a quantization/artifact table.

Columns:

- variant/quantization;
- file/shards;
- download size;
- estimated RAM;
- estimated VRAM;
- fit badge;
- recommendation reason;
- download/local status.

Primary action: Download.

Highlight one recommended option when confidence is sufficient, but keep all choices selectable.

For gated/private access failures:

- explain access/token requirement;
- link user to Settings -> Hugging Face token configuration;
- do not show raw provider authorization headers/errors.

## 20. Direct URL download

Discover or Downloads should include “Download from URL”.

Form:

- HTTP/HTTPS URL;
- resolved filename preview;
- size/range support if discoverable;
- optional safe filename override if supported;
- warning when LAN/private-network URL access is disabled by SSRF policy.

After submission, navigate/show the download job.

## 21. Downloads page

Sections/tabs:

- Active
- Completed
- Failed/History

Each job shows:

- provider/source display name;
- logical artifact/quantization;
- state;
- progress;
- completed/total bytes;
- transfer speed;
- ETA when meaningful;
- shard progress for split models;
- retry count;
- error summary.

Actions based on state/role:

- Cancel;
- Retry;
- Resume where explicit;
- Remove partial data;
- Create model from completed artifact;
- Delete completed artifact (Admin only and only through safe dependency checks).

## 22. API page

Purpose: make it easy to connect clients.

Show:

- base URL derived from current deployment/external URL setting where possible;
- OpenAI-compatible endpoint overview;
- configured public model IDs;
- copyable example configuration snippets for OpenAI-compatible clients and LiteLLM;
- API key management for Admin;
- non-Admin users see connection information but not secret key administration according to RBAC.

For a newly created API key:

- show plaintext exactly once;
- prominent Copy action;
- explicit warning it cannot be viewed again;
- require user to close/acknowledge the dialog.

Do not later render a masked value that suggests the full key can be recovered.

## 23. Settings — General

Potential controls:

- models directory display/path if supported as configurable;
- default startup timeout;
- default idle timeout;
- default priority;
- default routing policy;
- external/base URL behavior where needed;
- low-disk-space threshold;
- direct URL LAN/private-network policy.

Settings that require restart should say so before save.

## 24. Settings — llama.cpp

Show:

- detected binary path/identity;
- version/build;
- backend;
- schema discovery status/time;
- Refresh capabilities action;
- global llama.cpp defaults using Basic/Advanced views;
- impact preview for running models that would become restart-required.

Do not provide arbitrary shell command execution.

## 25. Settings — Authentication / Users

Admin only for administration.

Show users table:

- username;
- role;
- enabled;
- last login;
- actions.

Actions:

- create user;
- change role;
- enable/disable;
- reset password through explicit workflow;
- delete if allowed.

Prevent/clearly block leaving zero enabled administrators.

Current user menu provides self-service password change/logout.

## 26. Settings — Hugging Face

Admin page:

- token status: configured/not configured;
- Set/Replace token;
- Remove token;
- Test connection/auth action if useful;
- brief explanation that gated repositories require access already granted to the Hugging Face account.

Never populate a password field with the stored token.

## 27. Settings — Resource policy

Show scheduler-relevant global controls that are truly user-adjustable, such as:

- memory safety margin if exposed;
- default priority;
- eviction behavior explanation;
- Always-On unsatisfied status;
- detected hardware.

Avoid exposing every scheduler scoring coefficient in v1. The policy should remain understandable.

## 28. Responsive behavior

Desktop is primary, but:

- navigation collapses on narrow screens;
- model table can switch to stacked rows/cards;
- essential lifecycle buttons remain reachable;
- charts can reduce detail rather than overflow;
- long CLI option names wrap/copy cleanly;
- dialogs fit viewport and remain keyboard usable.

## 29. Accessibility

Requirements:

- keyboard navigable forms/dialogs;
- visible focus states;
- form labels associated correctly;
- state/fit/error meaning not communicated only by color;
- sufficient contrast;
- live loading/progress states with accessible text;
- icons include text/tooltips/accessible names where necessary.

## 30. Notifications

Use transient toasts for completed immediate actions such as settings saved or start requested.

Use persistent inline banners/alerts for conditions requiring action, such as:

- model failed;
- restart required;
- Always-On unsatisfied;
- low disk space;
- provider auth invalid.

Do not rely on a toast for important failure details that disappear before the user can read them.

## 31. Confirmations

Require explicit confirmation for destructive/high-impact actions:

- delete model definition;
- delete artifact files;
- cancel/remove large partial download when data will be lost;
- replace/remove Hugging Face token;
- disable/delete user;
- broad global config change affecting many running models, when appropriate.

Routine Start should not require a confirmation. Stop may require one only when active traffic or special policy makes the impact significant.

## 32. Empty states

Every primary page needs a useful first-run empty state.

Examples:

### No models

Explain the two paths:

- Discover on Hugging Face;
- download/import from direct URL/existing artifact workflow.

### No downloads

Point to Discover.

### No metrics

Explain that metrics appear after inference traffic.

### No API keys

Admin gets Create API key CTA.

Avoid empty tables with no guidance.

## 33. Loading and polling

Management API is REST-only in v1.

Use polling strategically:

- dashboard/resource state: moderate periodic polling;
- active model lifecycle: faster while transition is occurring, slower when stable;
- download progress: faster while visible/active;
- logs: polling only while log view/auto-refresh is active;
- hidden browser tabs should reduce polling where possible.

Do not make every component independently poll the same endpoint at high frequency; use shared stores/query caching.

## 34. Frontend state management

Use Nuxt/Vue conventions and a consistent data-fetch/query state layer.

Requirements:

- backend remains source of truth;
- optimistic UI only for actions where rollback is safe;
- lifecycle state should primarily follow server responses/polls;
- unsaved form state is clearly separated from saved server config;
- auth/session expiry globally redirects/prompts appropriately;
- role/capability data is centralized for UI gating.

Exact library selection is an implementation decision.

## 35. Error presentation

API errors should be mapped into:

- concise user-facing message;
- optional technical details expandable for operators;
- correlation/request ID where available;
- suggested next action when obvious.

Examples:

- insufficient resources -> show required vs available and likely eviction constraints;
- unsupported llama.cpp option -> link Configuration;
- startup failure -> link Logs;
- Hugging Face 401/403 -> link credential/access guidance;
- missing GPU -> link Instances GPU assignment.

Do not dump raw stack traces into normal UI.

## 36. RBAC presentation

Backend authorization is authoritative, but UI reflects role:

- Read-only: no mutation buttons/forms;
- Operator: lifecycle/model config/download operations available; security/destructive/global admin controls absent;
- Admin: full controls.

If an endpoint returns 403 because role changed while UI was open, show a clear authorization message and refresh current-user capabilities.

## 37. Terminology

Use consistent product terms:

- **Model** — configured public model;
- **Artifact** — downloaded/local GGUF files;
- **Instance** — manually configured/running worker slot;
- **Public model ID** — value clients send in `model`;
- **Always On** — keep at least one instance available;
- **Autoload** — load when requested;
- **Idle timeout** — unload after inactivity;
- **Restart required** — saved desired config differs from running process;
- **Discover** — browse providers.

Avoid calling every artifact a “model instance” or exposing internal `llama-server` terminology unnecessarily.

## 38. v1 primary user journey

The complete intended journey is:

1. First-run Admin setup.
2. Open Discover.
3. Search Hugging Face.
4. Open a repository.
5. Compare GGUF quantizations and hardware fit.
6. Choose recommended or another artifact.
7. Download and monitor progress.
8. Create a Model from completed artifact.
9. Choose public model ID.
10. Configure Basic llama.cpp options.
11. Configure GPU placement/tensor split.
12. Set Autoload, Always-On, idle timeout, priority and routing policy.
13. Save and optionally Start.
14. Watch STARTING/LOADING -> READY.
15. Create an API key in API page.
16. Connect an OpenAI-compatible client or LiteLLM.
17. Observe request/throughput/latency metrics.
18. Allow a non-Always-On model to idle-unload.
19. Send another request and see transparent autoload.

The UI design should make this flow possible without requiring the user to understand worker ports or manually write llama.cpp command lines.

## 39. UI invariants

1. Worker ports are never required for normal user workflows.
2. Public model ID is visually prominent.
3. Saved desired config and active running config are never conflated when restart is required.
4. Every discovered llama.cpp option is reachable from Advanced configuration.
5. Always-On policy conflict is explained rather than creating a stop/restart loop in the UI.
6. Missing GPU assignments are preserved and shown as errors, not silently changed.
7. Recommendations remain optional.
8. Deleting a model and deleting its artifact are separate flows.
9. API key plaintext is shown only on creation/rotation.
10. Read-only users cannot initiate mutations through visible UI controls.

## 40. Acceptance criteria

The UI is v1-complete when a user can:

- bootstrap/login securely;
- see hardware and operational status on Dashboard;
- browse/filter/sort configured models;
- inspect all lifecycle states and failures;
- start/stop/restart allowed models;
- create and edit a model without command-line knowledge;
- use both Basic and searchable Advanced llama.cpp configuration;
- see inheritance/overrides and restart-required state;
- configure one or multiple manual instances with visual GPU/tensor split controls;
- browse Hugging Face and see hardware-aware quantization recommendations;
- download normal and split GGUF artifacts with progress/error handling;
- create a model from a completed download;
- manage API keys according to role;
- view OpenAI/LiteLLM connection guidance;
- inspect per-model metrics and per-instance logs;
- configure Hugging Face authentication and global defaults as Admin;
- use the essential status/actions on a narrow/mobile viewport;
- complete the full primary user journey described above without direct access to a worker port or manual llama-server CLI invocation.
