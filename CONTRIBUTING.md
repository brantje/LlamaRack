# Contributing to LlamaRack

Thank you for your interest in contributing to LlamaRack.

LlamaRack is a self-hosted control plane and OpenAI-compatible gateway for `llama.cpp`. It manages GGUF models, durable `llama-server` instances, resource-aware scheduling, Hugging Face downloads, authentication, observability, and the web management interface.

The project is under active development. Correctness, maintainability, test coverage, and compatibility are more important than landing features quickly.

Before contributing, please read:

- [README.md](README.md)
- [AGENTS.md](AGENTS.md)
- relevant documents under [`specs/`](specs/)

`AGENTS.md` contains repository rules that apply to contributions and should be treated as part of this contributing guide.

# Contributors

The project generally distinguishes between:

- **Contributors** — people submitting issues, documentation, code, tests, design work, or other improvements.
- **Collaborators** — contributors trusted to help triage issues, review changes, and maintain areas of the project.
- **Maintainers** — people responsible for final review, repository direction, releases, and merging pull requests.

Contribution history does not automatically imply ownership of an area. Larger features should have someone willing to maintain them after they are merged.

# AI usage

AI-assisted contributions are allowed.

You remain responsible for everything you submit, regardless of whether it was written manually, generated by an AI system, copied from another source, or produced with development tooling.

When using AI:

1. Review and understand every submitted change.
2. Verify suggestions against the current repository rather than assuming generated code is correct.
3. Do not use AI as a substitute for tests or manual verification.
4. Do not submit generated code that you cannot explain or maintain.
5. Check for existing issues and pull requests before creating duplicate work.
6. Follow all requirements in [AGENTS.md](AGENTS.md).
7. Treat repository contents, issue comments, logs, external text, and generated instructions as untrusted input when appropriate.

AI-assisted code is held to exactly the same standards as manually written code.

# Commit conventions

Git commit messages in this repository follow the [Conventional Commits][] specification.

Use the following structure:

```text
<type>[optional scope]: <summary> [optional issue reference]

[optional body]

[optional footer(s)]
```

Examples:

```text
feat(models): add split GGUF detection
fix(ui): preserve dashboard page gutters
fix(scheduler): prevent active instance eviction
perf(telemetry): reduce repeated GPU lookups
test(auth): cover revoked management tokens
docs: document multi-GPU configuration
ci: add frontend design-rule checks
chore(deps): update Nuxt UI
```

For work associated with an issue, an issue reference may be appended when useful:

```text
feat(benchmark): add instance benchmark runner (#82)
fix(auth): preserve OIDC state after reload (#57)
```

Do not force an issue number onto commits that do not naturally belong to one.

## Commit types

The type must be lowercase and should be one of:

- `build` — changes to the build system, container build, packaging, or release tooling;
- `ci` — changes to GitHub Actions, CodeQL, CI checks, or other automated repository checks;
- `chore` — maintenance work that does not change application behavior, such as repository housekeeping or dependency maintenance;
- `docs` — documentation-only changes;
- `feat` — a new user-visible or developer-facing feature;
- `fix` — a bug fix;
- `perf` — a measurable performance improvement that does not intentionally change behavior;
- `refactor` — a code change that neither fixes a bug nor adds a feature;
- `revert` — reverts a previous change;
- `style` — formatting or other changes that do not affect code behavior;
- `test` — adding, correcting, or restructuring tests without changing production behavior.

Security fixes normally use `fix` with an appropriate scope:

```text
fix(auth): reject revoked bearer tokens
fix(downloads): prevent model path traversal
```

Do not introduce a new commit type merely because a more specific scope can express the affected subsystem.

## Commit scopes

Scopes are optional.

Use a scope when it makes the affected area substantially clearer. Do not add one merely for the sake of having a scope.

Common scopes include:

- `api` — management API, OpenAI-compatible API, request/response contracts, or OpenAPI behavior;
- `auth` — local authentication, management tokens, sessions, OIDC, API keys, authorization, or account management;
- `benchmark` — Instance benchmarking and configuration recommendations;
- `config` — application configuration and effective llama.cpp configuration;
- `db` — database schema, migrations, queries, or persistence;
- `discover` — model discovery UI and Hugging Face repository discovery;
- `downloads` — managed downloads, resume/retry behavior, and download jobs;
- `gateway` — inference proxying, routing, streaming, and OpenAI-compatible request handling;
- `hf` — Hugging Face integration;
- `instances` — Instance configuration, state, lifecycle, and management;
- `logs` — Instance logs, request logs, and tracing;
- `metrics` — Prometheus metrics and application metrics;
- `models` — GGUF models, metadata, registration, scanning, and model defaults;
- `runtime` — `llama-server` process execution and runtime integration;
- `scheduler` — GPU placement, VRAM/RAM accounting, eviction, autoload, queues, and resource scheduling;
- `telemetry` — CPU, RAM, GPU, VRAM, and process telemetry;
- `ui` — frontend UI or shared frontend behavior;
- `docker` — Dockerfiles, Compose configuration, runtime images, and container behavior;
- `deps` — dependency updates;
- `release` — release and publication automation.

These scopes are guidance, not an exhaustive registry.

Prefer the smallest meaningful scope:

```text
fix(scheduler): preserve VRAM reserve during placement
```

rather than:

```text
fix(backend): preserve VRAM reserve during placement
```

Likewise, use `ui` when the change genuinely spans the frontend rather than inventing a scope for an individual page:

```text
fix(ui): keep NuxtPage mounted during authentication
```

If a change genuinely spans several subsystems, omit the scope instead of creating a combined one:

```text
feat: add multi-node manager support
```

Do not use filesystem paths as scopes.

## Commit summary

The summary should be a short description of the change.

- use the imperative, present tense: `add`, not `added` or `adds`;
- start with a lowercase letter;
- do not end with a period;
- describe the result rather than the implementation mechanics;
- keep the complete header around 72 characters where practical;
- aim for approximately 50 characters for the summary itself when that remains descriptive.

Good:

```text
fix(scheduler): protect active requests from eviction
```

Less useful:

```text
fix(scheduler): changed some scheduler code
```

Avoid vague messages such as:

```text
fix: fixes
chore: changes
refactor: cleanup
feat: updates
```

## Commit body

A commit body is strongly recommended for non-trivial changes.

Use it to explain **why** the change is necessary and, where useful, contrast the new behavior with the previous behavior.

The diff already explains most of **how** the change was implemented.

Example:

```text
fix(scheduler): protect active requests from eviction

Resource-pressure eviction could select an Instance while it still had
active inference requests. This could terminate an otherwise healthy
stream when another Instance needed VRAM.

Exclude Instances with active requests from normal eviction candidates.
```

Use the imperative, present tense where practical.

Wrap body lines at approximately 72 characters.

A body is generally unnecessary for obvious, self-contained changes such as:

```text
docs: fix broken installation link
```

or:

```text
chore(deps): update Nuxt UI
```

## Breaking changes

Breaking changes must be explicit.

Use `!` after the type or scope:

```text
feat(api)!: rename Instance lifecycle fields
```

or add a `BREAKING CHANGE` footer:

```text
feat(api): replace legacy Instance state response

BREAKING CHANGE: clients must use lifecycle_state instead of state.
```

Breaking changes require a particularly strong justification because this project exposes persistent configuration, management APIs, OpenAI-compatible APIs, and deployment interfaces.

Document any required migration in the pull request and relevant project documentation.

## Commit footers

Footers are optional and use Conventional Commit trailer syntax:

```text
<token>: <value>
```

Examples:

```text
Refs: #82
```

```text
BREAKING CHANGE: remove the deprecated configuration field.
```

Prefer linking or closing issues in the pull request when several commits belong to the same issue rather than repeating the same issue metadata on every commit.

## Reverts

Revert commits should clearly identify the reverted change.

For example:

```text
revert: add automatic tensor split recommendation

Reverts commit 0123456789abcdef.
```

Follow the recommendations in the [Conventional Commits specification][Specification] when applicable.

## Pull request and squash titles

Pull request titles should follow the same Conventional Commit format because pull requests are normally squash-merged.

Examples:

```text
feat(benchmark): add Instance benchmarking
fix(auth): restore OIDC provider after reload
feat(ui): redesign Instance details
docs: overhaul contributor documentation
```

The final squash commit should therefore also follow Conventional Commits.

Do not use GitHub's default merge message as the final commit message for a squash merge.

The pull request description should contain the detailed rationale, testing performed, compatibility implications, and relevant issue links. The squash commit body may retain the important reasoning when useful for understanding repository history.

## Commit hygiene

Keep commits logically coherent.

A commit should ideally represent one meaningful unit of change that can be reviewed and understood independently.

Avoid combining unrelated work such as:

```text
feat(models): add metadata detection + redesign navbar + update deps
```

Split unrelated changes instead.

Do not create separate commits solely for:

- fixing formatting introduced by the immediately preceding commit;
- making tests pass after knowingly committing incomplete production code;
- addressing trivial review feedback;
- generated files that belong to the same logical change.

Before opening a pull request, contributors may clean up their own branch history when doing so makes the change easier to review.

Do not rewrite shared branch history without coordinating with other contributors.

## Commit reminders

- The blank line between the commit header and body is required.
- Keep commit messages understandable without needing the associated pull request.
- Prefer explaining **why** over narrating the diff.
- Use scopes consistently but not excessively.
- Mark breaking changes explicitly.
- Keep unrelated changes in separate commits and pull requests.
- Pull request titles should follow Conventional Commits as well.
- See [Conventional Commits][] for the complete specification.

# Pull requests

## Before you start

Search existing:

- issues;
- discussions;
- pull requests;
- specifications.

Avoid creating duplicate implementations.

### Features

Significant new features should begin with an issue or design discussion before implementation.

A feature proposal should establish the expected behavior, including relevant:

- product behavior;
- UX;
- API contracts;
- data model;
- lifecycle;
- defaults;
- edge cases;
- compatibility;
- persistence;
- migration;
- testing;
- operational behavior.

For a feature, phase, or substantial implementation slice, follow the clarification requirements in [AGENTS.md](AGENTS.md). Do not silently invent important requirements where the intended behavior has not yet been established.

Small, obvious, isolated improvements do not require unnecessary planning ceremony.

### Bug fixes

Bug fixes should include:

1. a clear description of the incorrect behavior;
2. a reproducible case where practical;
3. identification of the underlying cause rather than only the visible symptom;
4. a regression test that fails without the fix and passes with it.

Avoid fixes that simply special-case one observed input while leaving the underlying bug intact.

### Public interfaces

Changes to public or persisted interfaces have a higher bar than internal refactoring.

Take particular care when changing:

- `/v1/*` OpenAI-compatible endpoints;
- management APIs;
- OpenAPI schemas;
- WebSocket or streaming protocols;
- configuration variables;
- persisted configuration;
- database schemas;
- model or Instance identifiers;
- authentication behavior;
- inference API-key behavior;
- llama.cpp argument generation.

Compatibility changes must be intentional and documented.

# Preparing your pull request

Keep pull requests focused.

Prefer one feature or one bug fix per PR.

Do not combine unrelated refactoring, formatting, dependency upgrades, and behavioral changes unless they are required for the same change.

Before publishing a PR:

- inspect your diff;
- remove unrelated changes;
- add or update tests;
- update documentation when behavior changed;
- run the relevant validation locally;
- verify that existing behavior has not unintentionally changed.

## Repository layout

The primary application components are:

```text
backend/     Go backend and control plane
frontend/    Nuxt management UI
specs/       Product and architecture specifications
```

Keep dependencies, tests, and build tooling inside the appropriate application root unless there is a clear repository-wide reason not to.

# Backend contributions

The backend is written in Go.

Prefer:

- clear, idiomatic Go;
- small interfaces;
- explicit error handling;
- standard-library functionality where practical;
- context-aware operations;
- deterministic tests;
- straightforward concurrency;
- simple code over clever abstractions.

Avoid adding dependencies unless they provide a clear benefit that is difficult to achieve safely with the existing stack.

## Backend validation

Run from `backend/`:

```bash
go mod tidy
go test ./... -covermode=atomic -coverprofile=coverage.out
go tool cover -func=coverage.out
go vet ./...
```

Backend statement coverage must remain at **90.0% or higher**.

For changes involving concurrency, scheduling, process lifecycle, streaming, shared state, authentication, or other race-sensitive code, also run:

```bash
go test -race ./...
```

Tests should not depend on:

- a real GPU;
- a real model;
- external network access;
- Hugging Face availability;
- an externally running `llama-server`.

Use temporary directories, temporary SQLite databases, fake HTTP servers, and local process fixtures where appropriate.

## Backend testing

Tests should verify behavior, not merely execute lines.

Cover important:

- success paths;
- error paths;
- validation failures;
- authorization failures;
- persistence behavior;
- lifecycle transitions;
- concurrency invariants;
- cleanup behavior.

Regression fixes must include a regression test.

Changes to resource scheduling should test realistic resource combinations and failure paths rather than only trivial cases.

Changes involving `llama-server` configuration should verify the resulting effective arguments or environment, not only the stored configuration.

# Frontend contributions

The frontend is a Nuxt application using Nuxt UI and Tailwind.

Nuxt UI components are the first choice for interface development.

Use this priority:

1. existing Nuxt UI component;
2. Nuxt UI props, variants, slots, and theme configuration;
3. Tailwind utilities;
4. shared Tailwind/Nuxt UI theme tokens;
5. narrowly scoped custom CSS only when the above cannot express the requirement.

Do not recreate existing Nuxt UI primitives with custom HTML and CSS.

When modifying legacy frontend areas, move the touched surface toward Nuxt UI + Tailwind rather than extending the old CSS system.

Preserve the existing application theme unless the task explicitly includes a redesign.

## Frontend design invariants

Do not nest card surfaces inside other cards.

For hierarchy inside a card, prefer:

- sections;
- separators;
- tables;
- alerts;
- disclosures;
- spacing;
- typography.

Native browser confirmation dialogs are prohibited.

Do not use:

```js
confirm()
window.confirm()
globalThis.confirm()
```

Use a Nuxt UI overlay such as `UModal`.

Destructive or availability-impacting actions should explain their consequences before confirmation.

## Nuxt routing

The Nuxt page mount invariant must never be broken.

`frontend/app/app.vue` must contain exactly one unconditionally mounted:

```vue
<NuxtPage />
```

Do not:

- conditionally mount `<NuxtPage />`;
- replace it with `<RouterView />`;
- conditionally omit a layout's default `<slot />`;
- disable Nuxt pages merely to suppress routing errors.

Loading, authentication, authorization, and backend-error states must be implemented without violating this invariant.

`[NUXT_E4011] Your project has pages but the <NuxtPage /> component has not been used` is considered a regression.

## Frontend validation

From `frontend/`:

```bash
npm install
npm run test:coverage
npm run build
```

Frontend coverage must remain at **90.0% or higher** for:

- statements;
- branches;
- functions;
- lines.

New frontend behavior must include corresponding tests.

# llama.cpp integration

LlamaRack manages `llama-server`; it should not unnecessarily replace or reinterpret llama.cpp's configuration model.

When working on llama.cpp integration:

- preserve upstream option semantics where possible;
- prefer discovering supported options from the installed binary instead of maintaining unnecessary duplicate definitions;
- keep manager-owned arguments under manager control;
- consider CPU and GPU deployments;
- consider single-GPU and multi-GPU configurations;
- consider older/newer llama.cpp versions where compatibility is relevant;
- do not assume CUDA is available;
- do not assume all llama.cpp builds expose identical capabilities.

Take particular care around:

- context size;
- KV cache;
- GPU layers;
- device selection;
- tensor split;
- parallelism;
- speculative decoding;
- multimodal projectors;
- environment variables;
- worker bind addresses and ports.

Generated `llama-server` command lines should be tested as complete behavior. A configuration option being saved correctly is insufficient if it is not ultimately passed to the worker correctly.

# Models and Instances

The distinction between **Models** and **Instances** is fundamental.

A **Model** represents a GGUF artifact and reusable defaults.

An **Instance** represents one durable `llama-server` configuration.

Do not introduce behavior that implicitly treats these as interchangeable.

In particular:

- one Model may have multiple Instances;
- Instance state belongs to the Instance;
- the OpenAI-compatible `model` identifier maps to an Instance slug;
- requests should not silently move to another Instance merely because it uses the same Model.

Changes in this area should preserve these semantics unless an explicitly approved design changes them.

# Scheduling and lifecycle

Instance scheduling and lifecycle code is correctness-sensitive.

Changes involving:

- VRAM accounting;
- RAM accounting;
- GPU placement;
- eviction;
- autoload;
- Always-On reconciliation;
- idle unload;
- process startup;
- process shutdown;
- active-request protection;
- request queues;

must include tests for both normal operation and failure/pressure conditions.

Do not assume estimated model size exactly equals runtime memory consumption.

Where runtime measurements exist, distinguish measured values from estimates.

Active inference requests must not be disrupted by normal eviction behavior unless the relevant feature explicitly defines otherwise.

Concurrency changes should be checked with the race detector.

# Security-sensitive changes

Authentication, authorization, filesystem access, downloads, proxying, process execution, and configuration handling are security-sensitive.

When changing them:

- validate user-controlled input server-side;
- avoid shell execution for constructed commands;
- keep credentials out of logs;
- do not return stored secrets as plaintext;
- protect filesystem boundaries;
- use bounded network and request operations;
- preserve authentication and authorization on streaming/WebSocket paths;
- test negative authorization cases;
- consider SSRF when accepting URLs;
- consider path traversal when accepting filenames or paths.

Security fixes should address the violated invariant rather than blacklist a single malicious payload.

# Performance changes

Do not optimize based on assumptions alone.

For non-trivial performance changes:

1. establish a benchmark or measurable baseline;
2. identify the actual bottleneck;
3. make the smallest useful optimization;
4. repeat the measurement;
5. verify correctness;
6. keep the change only when the improvement justifies its complexity.

Do not trade correctness, safety, or maintainability for insignificant benchmark improvements.

# Dependencies

Avoid unnecessary third-party dependencies.

Before adding one, consider:

- whether the standard library or an existing dependency already solves the problem;
- maintenance activity;
- security history;
- transitive dependencies;
- binary/container size;
- whether the dependency is required in production;
- whether its benefit justifies long-term maintenance.

Do not include unrelated dependency upgrades in a feature or bug-fix PR.

# Coding guidelines

## Go

Follow normal Go conventions.

Format changed Go files in place before committing:

```bash
gofmt -w <changed-go-files>
```

Prefer names and structures consistent with surrounding code.

Avoid speculative abstractions.

Handle errors explicitly.

Do not introduce `unsafe` without an exceptional and measured justification.

## TypeScript / Vue

Follow existing conventions in `frontend/`.

Prefer:

- typed data structures;
- composables for reusable application behavior;
- Nuxt-native patterns;
- Nuxt UI components;
- semantic Tailwind utilities;
- shared theme configuration over repeated hard-coded visual values.

Avoid introducing another frontend component or styling framework when Nuxt UI already provides the required functionality.

# Naming

Follow the conventions of the language and the surrounding package.

For Go:

- exported identifiers use `PascalCase`;
- unexported identifiers use `camelCase`;
- package names should be short and lowercase;
- avoid unnecessary repetition in names.

For Vue/TypeScript, follow the established conventions in the frontend.

Existing public names should not be changed solely for aesthetic consistency.

# Documentation

Documentation is part of the change.

Update documentation when you change:

- configuration;
- public API behavior;
- deployment requirements;
- authentication;
- model management;
- Instance lifecycle;
- Docker behavior;
- supported hardware;
- user-visible workflows.

If understanding a feature requires reading the implementation, consider adding the missing explanation to the relevant documentation.

Keep examples executable and consistent with current behavior.

# After submitting your pull request

Expect review comments concerning:

- correctness;
- test coverage;
- architecture;
- UX consistency;
- security;
- compatibility;
- maintainability.

Respond to the underlying concern rather than mechanically applying suggested patches.

If the target branch has moved significantly, update your branch before final review.

Keep the PR focused while addressing review feedback. Avoid opportunistic unrelated cleanup.

CI must pass before merge.

# Pull requests for maintainers

Before merging:

- understand the change;
- verify that the implementation matches the agreed behavior;
- verify relevant tests;
- verify the 90% coverage gates;
- check for unrelated changes;
- consider compatibility and migration effects;
- wait for required CI;
- confirm security-sensitive behavior where applicable.

Prefer squash merging unless there is a specific reason to preserve individual commits.

The pull request title should be used as the squash commit title and must follow the Conventional Commits rules in this guide.

Be mindful of long-term maintenance. Most of the cost of a feature occurs after it has been merged.

A pull request may be declined or closed when, for example:

- it duplicates existing work;
- it conflicts with an established design;
- it introduces significant complexity without sufficient benefit;
- required tests are missing;
- coverage requirements are not met;
- the contributor cannot explain or maintain the submitted implementation;
- it violates repository rules;
- the feature does not fit the project's scope.

Passing tests does not by itself guarantee that a change will be merged.

# Code maintenance

When adding a substantial subsystem, consider who will maintain it.

New code should:

- follow existing architecture where practical;
- include meaningful tests;
- have clear ownership boundaries;
- avoid unnecessary coupling;
- expose enough observability to diagnose failures;
- clean up resources correctly;
- document important invariants.

Do not leave known correctness problems to later cleanup issues simply because the happy path works.
